# AutoLL-3 v1.9.1

Codex reviewed 1.9.0, kept its changes, and found three follow-ups in how a
protection ends. This fixes all three and takes its advice on wording.

- **A clear gives back only the hold it is about.** When you clear a booking's
  protection, Autopilot gives back the hold it took for that request, so it can
  try again. It used to give back whatever hold it had on the attraction. In a
  page started after a later request took that hold, or with another tab
  holding it, the old clear let go of the newer request's hold. The hold now
  records the request it was taken for, and a clear releases that one and no
  other. A hold inherited from another tab, or from the page before a reload,
  is not released by a clear: it gives way once Plans have twice shown no
  booking, as inherited holds always have. So after a reload, Autopilot tries
  again a little later than it would have.
- **Autopilot hears of every clear.** It learned of a clear from Activity's
  record of the day, which is written best-effort, so a clear Activity failed
  to record left the attraction held for nothing. A clear now has a record of
  its own, written before the protection is removed. If that record cannot be
  written, the protection stays and the panel says why. Activity's list only
  reports.
- **A pass after midnight counts on its park day.** A pass the app could not
  read was placed on its calendar date, but a return time before 4am belongs
  to the park day before, which is where its protection is. A cancellation in
  doubt at 12:30am read its own day as complete, and cleared. An unreadable
  pass is now placed exactly as a readable one would be, and on both days it
  may be when its time cannot be read.
- **The one-tap note says what is known.** "Probably did not go through"
  claimed a likelihood nobody measured. Beside the button it now says: *No
  booking was visible in the last complete Plans check. The original request
  may still complete. Clearing permits another attempt.*

Each code change above has a test that fails against 1.9.0's code. 20 of the
24 new or changed tests do, run against 1.9.0 with stand-ins that behave as
1.9.0 did for the two functions 1.9.1 adds; the other four check behavior
1.9.0 already had right.

Verified locally, in a clean checkout of this change with a fresh install: 135
suites and 2,179 tests passed in four full runs, and no test ends with a load
still showing; lint, TypeScript checking, Prettier and the production build
passed; the dependency audit reported zero vulnerabilities. In the harness,
against fake clients, a booking Plans had not shown carried the new note beside
its one-tap clear. No real Disney reservation was created or modified for these
checks.
