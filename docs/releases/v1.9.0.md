# AutoLL-3 v1.9.0

Codex reviewed 1.8.5 and found three ways a reservation's protection could end
without proof, and a rule in the plan that is no longer Disney's. This fixes
all four. It also puts Autopilot's own lost bookings into the shared
protection, the one request left from Codex's review of 1.8.4.

- **Plans settle a protection only on what they could have shown.** The
  itinerary reader skipped a pass it could not read, such as a DAS selection
  whose guests' details were missing, and read an answer with no list of items
  as an empty itinerary. Both look exactly like passes that are gone, so a
  cancellation in doubt cleared as done whether or not it was. Now a missing
  pass counts only from a read that could have shown it, judged by attraction
  and day. Autopilot's own record of its bookings follows the same rule, and
  the Plans tab says when a read was incomplete.
- **A protection saved by 1.8.4 still protects.** 1.8.4 saved every lost
  cancellation under the ride's Lightning Lane key, DAS ones included. 1.8.5
  gave DAS selections their own key and read such a record as a Lightning Lane
  one, so it left the DAS key unguarded and looked done on the next read.
  Saved protections now carry a version. A cancellation saved before could have
  been either kind, so it guards both and clears only when Plans show neither.
  The test starts from what 1.8.4's own code stored.
- **A booking clears only on proof:** Plans showing any of its guests holding
  the attraction, Disney's own late answer, or you. It used to clear when Plans
  read 30 seconds after the request still showed nothing. Such a read now marks
  it as probably not made, and clearing it takes one tap in the protection
  panel instead of two.
- **Autopilot's own lost bookings are protected like any other change.** They
  were held by Autopilot's action ledger alone, which no booking, change or
  cancel by hand read, and which nobody could clear. Now they appear in the
  protection panel, pause the attraction for actions by hand too, and alert the
  phone: *No answer from Disney*. Clearing one lets Autopilot try the attraction
  once more.
- **Activity records how each protection ended:** confirmed by Disney's Plans,
  Disney answered, or cleared by you, with the time.
- **The plan's 120-minute rule was Genie+'s.** Under Lightning Lane Multi Pass
  the next selection opens when you redeem one or when its arrival window
  passes. `docs/PLAN.md` now says so, and the refutation of a "cascade" model
  that rested on the old rule is withdrawn: whether Autopilot should prefer
  earlier return times is open again (`docs/FUTURE.md` §4.5). The app never
  used the rule; it reads when the next booking opens from Disney's tip board.

**What clearing cannot rule out.** Disney may still apply a request whose
answer was lost, at any time, and no interval rules that out. Clearing a
protection is a judgment made after checking Plans, not proof. A lost booking
that lands after you clear it can turn up as an extra pass, for example after
the attraction was booked again and that booking given up. A lost cancel can
remove whatever the pass has become. The notes for 1.8.4 and 1.8.5 said
Disney's refusal of a second booking made a lost booking harmless. That refusal
does not cover this case, and those notes now say so.

Each code change above has a test that fails against 1.8.5's code. 22 of the
32 new or changed tests do, run against 1.8.5 with stand-ins for the few
functions 1.9.0 adds; the other ten check behavior 1.8.5 already had right.

Verified locally, in a clean checkout of this change with a fresh install: 135
suites and 2,156 tests passed in four full runs, and no test ends with a load
still showing; lint, TypeScript checking, Prettier and the production build
passed; the dependency audit reported zero vulnerabilities. In the harness,
against fake clients: a booking Plans still did not show offered the one-tap
clear, which cleared it, and Activity listed it as cleared by you, beside a
cancellation stored without a version, as 1.8.4 stored them, which the
harness's Plans settled as confirmed. No real Disney reservation was created or
modified for these checks.
