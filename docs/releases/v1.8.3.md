# AutoLL-3 v1.8.3

Addresses all seven findings from the October 3, 2026 audit of `4d01832`.

- Manual booking, modification, cancellation, and post-booking guest cleanup
  now use reservation leases and the shared final dispatch lifecycle. Production
  LL mutations refuse missing safety control. Unknown outcomes persist across
  navigation, block competing actions, and use the existing reconciliation UI.
  Fresh automated bookings now persist uncertainty too. Late definite results
  resolve only the operation they answer.
- Party changes invalidate prepared automated actions and cached eligibility,
  including changes from another tab. Whole-party checks verify guest identities
  in both eligibility and the final offer.
- Slot capacity and pending successful bookings are tracked per guest. Swap
  victims must cover the affected group; split-party or unrelated reservations
  cannot stand in for that group's capacity.
- Booking responses are validated at runtime. Missing or unreadable successful
  results, invalid dates, and post-dispatch body failures require reconciliation,
  not another booking. Local preparation failures remain safely retryable.
- Backup restore prepares all values before writing and preserves exact raw
  originals. Rollback frees staged space and attempts every recovery. Persistent
  recovery failures retain an emergency export and offer recovery retry instead
  of claiming the original plan was restored.
- Sign-in shares SDK initialization, replaces failed script downloads, and bounds
  both loading and initialization with a 15-second deadline. Obsolete attempts
  cannot launch over a newer retry.
- Compatible development-tool security updates; loopback-only development by
  default, explicit LAN scripts, and a scheduled dependency-audit workflow.
  Stable build entry names preserve the installer contract. Rollup is pinned to
  security-patched 4.59.0 after a 4.64.0 tree-shaking performance regression.

Regression tests cover dispatch contention, navigation, late results, malformed
responses, party changes, per-person capacity, quota/rollback failures, and login
retry/StrictMode behavior. No real Disney reservation was created or modified
for these checks.
Final local verification: 128 suites and 2,038 tests passed; lint, TypeScript
checking, and the production build passed after a clean install. The complete
dependency audit reported zero vulnerabilities.
The harness was served locally, but no browser was connected for a visual or
device rehearsal in this release session.

The inherited runtime module and installer revisions remain unchanged. Existing
limitations remain explicit: cross-tab exclusion requires Web Locks, storage
failure can limit protection to the open page, and multi-key localStorage restore
is not crash-atomic. Check Disney's official Plans before resolving uncertainty.
